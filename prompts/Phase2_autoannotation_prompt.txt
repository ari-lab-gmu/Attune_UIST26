STAGE 2 INSTRUCTIONS: pattern_consultation
═══════════════════════════════════════════════════════
Stage 1.5 reminder: **candidate slots are possible evidence sources, not a mandatory checklist.**
Later stages must NOT emit a formal why item for every non-empty slot.

Goal: patterns do NOT pick the answer first. They only **weight pre-defined shift candidates**.

WRONG workflow (forbidden): pick a favorite pattern → bend the shift story to match it.
RIGHT workflow (required):
  (A) From TARGET SHIFT + Stage 1 only, define three fixed candidate slots per side (see schema).
      These rows use **shift_summary_one_line** + **verified_cue_paths** only — do NOT put a
      pattern_id in a candidate row in order to \"choose\" that pattern.
  (B) For **each** pattern in STAGE 2 INPUT, fill **patterns_weight_candidates**: how that pattern
      supports each slot on leave and on arrive. Stance values per slot:
        \"full\"    — this pattern clearly supports that candidate (same as “supports candidate X”)
        \"partial\" — partially supports that candidate
        \"none\"    — does not support that candidate for this shift
      A pattern may give full to one slot, partial to another, and none to the rest — that is normal.
      If the library lists K patterns, **patterns_weight_candidates** must contain exactly K objects
      (one per pattern_id, no duplicates, no omissions).
  (C) Merge (A)+(B): assign **sort_rank** on each candidate row (1 = best) using Stage-1 strength
      plus pattern weights (full > partial > none; use multiple patterns’ stances as corroboration).
  (D) Only after (C): set **leave_best_pattern_id** / **arrive_best_pattern_id** as the single
      pattern_id that best backs the **sort_rank=1** slot’s evidence_family (prefer full over
      partial; respect eligibility). If no pattern gives full/partial to that winning slot, use \"\".

The three candidate slots per side (fixed order in JSON):

  • robot_context      — anchor only on robot_context_cues for that side.
  • visual_change      — anchor only on visual_cues for that side (Stage-1 rules).
  • pattern_analogy    — a **hypothesis slot**: how this shift might resemble prior reviewed cases,
    stated from shift-visible facts + library *topics* — still no committing pattern_id here;
    pattern_ids enter only in **patterns_weight_candidates**.

If the pattern library is empty, **patterns_weight_candidates** is [] and ranking uses Stage-1 only.

Eligibility gate (applies when mapping patterns to sides):
  If core_signal_validation.per_pattern[pid].leave_core_signal_ok is false → for that pid,
  all **leave** stances in patterns_weight_candidates must be \"none\", and pid cannot be
  leave_best_pattern_id or selected in leave_match. Same for arrive / arrive_core_signal_ok.

Aggregate fields **leave_pattern_support** / **arrive_pattern_support** describe how strongly the
chosen **leave_best_pattern_id** / **arrive_best_pattern_id** backs the winning (sort_rank=1) slot:
   \"strong\"  — that pattern gave \"full\" toward that slot (or best available partial with strong Stage-1)
   \"partial\" — \"partial\" stance toward that slot
   \"none\"    — best_pattern_id is \"\" OR stance was none for the winning slot

HARD RULE — pattern cannot create evidence:
   If Stage 1 leave_support = "none" → leave_pattern_support is irrelevant; no formal why_leave.
   If Stage 1 arrive_support = "none" → arrive_pattern_support is irrelevant; no formal why_arrive.

HARD RULE — present state / view property cannot alone justify formal why:
   A present robot/view state alone cannot produce a formal why item. Fields may describe what exists
   in the frame without explaining why the participant shifted.
   Examples that are NOT sufficient by themselves (may only support a why if paired with change,
   contrast, corroborating visual evidence, or a strongly aligned eligible reviewed pattern):
     • to_view_is_gripper_camera = true
     • from_view_is_gripper_camera = true
     • gripper_status = Open / Closed (static snapshot without delta)
     • destination_salient_labels_at_shift alone (presence, not change)
   to_view_is_gripper_camera, from_view_is_gripper_camera, destination_salient_labels_at_shift describe
   **what the view has**, NOT **why the user shifted**. They can only be supporting/hypothesis/pattern-alignment
   cues unless upgraded per below. Formal why_leave / why_arrive MUST be grounded in **change evidence**
   or case_interpretation-approved meaningful explanation.
   Allow formal why ONLY when at least one holds:
     • labels_newly_visible_in_to_view non-empty (arrive) or labels_lost_from_from_view non-empty (leave)
     • behavior_fields_changed non-empty (robot state changed at shift)
     • from/to contrast exists and aligns with the reviewed pattern's signal
     • explicit current-shift cue indicating user was "looking at details"
   Otherwise → put in hint only; why must be [].

HARD RULE — newly visible object ≠ automatic arrive reason:
   A newly visible label is not automatically an arrive reason. Treat as formal why_arrive only if the
   whole case (Stage 1.5 + shift story) suggests **deliberate attention**, not incidental visibility.

     • dwell_after_sec is not short (not rapid scan / instantaneous glance)
     • gaze_cues.next_shift_within_1s = false (user did not shift away quickly)
     • object reads as operation target / object of interest, not background clutter
     • pattern's supporting_shift_ids are semantically similar to this shift
     • change_hypothesis has stronger task relevance, not just generic visual gain

OUTPUT QUALITY RULES (hints + formal why)

HINT STYLE RULES

Hints must be conservative and minimal.
A hint is only a weak possible interpretation, not a mini-explanation essay.

When generating leave_hint or arrive_hint:
  • prefer one short sentence
  • avoid strong narrative claims
  • avoid saying a pattern "aligns" unless the alignment is clearly meaningful
  • do not restate multiple weak cues as if they form a strong explanation
  • if the case is rapid_scan_glance, hints should sound brief and uncertain

Examples of good hints:
  • "The shift may reflect a quick check rather than a strong semantic reason."
  • "The destination view may offer broader monitoring context, but the evidence is weak."
  • "A new object became visible, but it is unclear whether it drove the shift."

Examples of bad hints:
  • long pattern-heavy narratives
  • explanations that sound stronger than the evidence
  • treating weak analogy as if it were participant intent

FORMAL WHY STYLE RULES

A formal why item should describe the meaningful reason for the shift,
not merely restate a field name or a raw state.

Good formal why items should:
  • sound like a participant annotation, not a database entry
  • summarize the reason at the right level
  • stay grounded in the anchor cue, but not be limited to copying it verbatim

Bad formal why items include:
  • pure field restatements
  • labels without human meaning
  • explanations that only say what existed, not why the participant shifted
