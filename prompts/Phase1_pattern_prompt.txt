You are extracting recurring PARTICIPANT-LEVEL PATTERNS from one multi-robot gaze-shift session.
PURPOSE: Your output will be shown to the SAME PARTICIPANT who made these annotations, 
so they can review, confirm, or edit the patterns. 
leave.user_says and arrive.user_says appear as editable chips. 
pattern_rule is shown as a first-person summary the participant can immediately recognize. 
review_question is shown as a prompt to guide their confirmation. 
Later, these patterns and their supporting_shift_ids will be used to select 
5 representative gaze shifts for annotation.

CRITICAL: Each annotated gaze shift is a 3-LAYER EXPLANATION UNIT:
  Layer 1 — Observable context: robot_context_cues + visual_cues + gaze_cues
  Layer 2 — Gaze-shift behavior: from_view, to_view, transition_type, dwell, density
  Layer 3 — Participant annotation: user_reason_leave_push / arrive_pull, explanation, shift_type
The annotation (Layer 3) is the participant's explanation of a shift situated in Layers 1+2.
NEVER model annotation separately from context and gaze behavior.
Participant-written reasons (Layer 3) are the PRIMARY source for what a pattern MEANS.
Robot/visual/gaze context (Layers 1+2) explains WHEN and WHY the pattern triggers.

SYSTEM: You analyze a HUMAN PARTICIPANT's eye-tracking, NOT the robot. 
'Pull' = what attracted gaze to a view (arrive); 'Push' = what made them look away (leave). 
Camera names (gripper/head/ceiling) are views the participant watched.

FOLLOW THESE STEPS IN ORDER before writing any JSON:

STEP 1 — Parse each shift as a 3-layer unit.
  For each annotated_shift_feature_bundle, read ALL THREE layers together:
    Layer 1 context:  robot_context_cues, visual_cues, gaze_cues
    Layer 2 behavior: from_view, to_view, transition_type, dwell_before/after, context_shifts (≤2 segments)
    Layer 3 annotation: user_reason_leave_push, user_reason_arrive_pull,
                        explanation, shift_type, memory_clarity, self_confidence
  Never read Layer 3 alone. Every annotation must be understood against its Layer 1+2 backdrop.

STEP 2 — Cluster by Layer 3 semantics (annotation-first) but need to consider joint shift logic from Layer 1+2.
  Group shifts whose user_reason_leave_push and user_reason_arrive_pull express the same intent.
  Same underlying situation explained differently = ONE cluster = ONE pattern candidate.
  Push + pull of the same trigger = still ONE cluster.
  Only after clustering by annotation: check whether Layers 1+2 are consistent within each cluster.
  SPLIT RULE: If a shift's leave_push and arrive_pull map to DIFFERENT clusters,
  prefer separate patterns or side-dominant assignment — do NOT force a single 'both' pattern
  to cover incompatible stories.

STEP 3 — For each cluster, characterize all three layers and set pattern_scope.
  Decide pattern_scope from evidence only (never for coverage quotas):
    leave_only:  only leave-side reasoning is substantive; set arrive empty.
    arrive_only: only arrive-side reasoning is substantive; set leave empty.
    both:        both sides have substantive material in this cluster.
  Do NOT invent a missing leave or arrive half. Single-sided patterns are valid.
  Each side you include must stand alone: a reader who only reads leave OR only arrive
  should still understand the pattern; do not split one idea across both sides.
  Layer 1+2 → leave.signal / arrive.signal (only for the side(s) in scope):
    What observable context (robot state, visual labels, gaze dynamics) co-occurs
    when the participant leaves / arrives? One sentence each.
  Layer 3 → leave.user_says / arrive.user_says (only for the side(s) in scope):
    2–4 SHORT ABSTRACTED phrases from the participant's own reasons — NOT raw quotes.
    TRANSFORM: 'robot1 | Status-Gripper | Closed cannot grab anything'
             → 'gripper closed, no manipulation progress'
    TRANSFORM: 'robot2 | Visual | ①bottle the bottle is close, could be target'
             → 'target object visible and reachable in destination view'
  shift_type_tendency: count Reactive/Proactive/Mixed across supporting shifts
  (exclude shifts where shift_type is empty).
  - If ≥70% agree → use that type.
  - Otherwise → 'Mixed'.
  - If ALL are empty → omit the field or set 'Mixed'.
  confidence: aggregate memory_clarity + self_confidence across the cluster.
    'Clearly remember' + 'High' → High; 'Guessing' / 'Low' → Low; mixed → Medium.

STEP 4 — Coverage verification (do this before writing JSON).
  Go through each shift_id in the valid list:
    <<<PLACEHOLDER FOR: valid hand-annotated shift_id list>>>
  For each shift_id:
    (a) Read its Layer 3 annotation.
    (b) Compare with clusters from Step 2.
    (c) If it matches an existing cluster → add to that pattern's supporting_shift_ids + evidence.
    (d) If it does not match any strong cluster → add to a Low-confidence catch-all, 
or omit if only 1–2 true outliers.
  PREFER: every shift_id in at least one pattern.
  After assigning all shift_ids, output a scratchpad line (in your reasoning, not in JSON):
  "COVERAGE CHECK: covered=[...], uncovered=[...]"
  If uncovered is non-empty, you MUST either:
    (a) add them to an existing pattern's supporting_shift_ids, or
    (b) create a catch-all pattern with confidence='Low'.
  Outputting JSON with uncovered shift_ids is a HARD FAILURE.

STEP 5 — Write pattern_rule and review_question for each pattern.
  pattern_rule: first-person sentence the participant will recognize immediately.
    Format: 'When [Layer 1+2 context], I tend to [Layer 3 explanation].'
    Example: 'When the gripper view shows no activity, I look away to check broader progress.'
  review_question: one concrete YES/NO or short-answer question for the participant.
    It should let them confirm, revise, or reject the pattern.
    Example: 'Does this match how you usually decide to switch away from the gripper view?'
