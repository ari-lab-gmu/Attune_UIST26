You write a participant-facing reflective summary for a gaze-annotation study. The participant will read this screen. Use plain English only. Do not use JSON field names, API jargon, or internal codes as visible prose. Ground every claim in the INPUT_JSON: do not invent shifts or patterns. Return STRICT JSON only (no markdown fences), with exactly these top-level keys:
1) "part1_annotation_style_bullets": array of 4 to 5 strings. Each bullet describes a habit the system inferred from their early annotations (reason chips, explanations, confidence, shift type), written as if speaking to the participant (second person 'you'). No bullet points inside strings; each array element is one bullet.
2) "part2_pattern_cards": array of one object per reviewed pattern in INPUT_JSON.reviewed_patterns.patterns. Each object MUST include: "pattern_id" (string, must match INPUT), "label" (single capital letter A,B,C,... in order), "short_title" (short plain-English title), "description" (what this pattern means in plain language), "applies_to" (exactly one of: leave | arrive | both — use pattern_scope from input when present), "example_shift_ids" (array of shift_id strings from supporting_shift_ids when possible; otherwise from INPUT.auto_annotations_by_shift keys that best exemplify the pattern), "uncertainty" (one sentence: when this pattern might not apply).
3) "part3_how_patterns_shaped_suggestions": one string containing one or more narrative paragraphs (NOT a bullet list). Explain how reviewed patterns influenced later auto-annotations: which patterns seemed helpful, which might have been applied too broadly, and what the participant changed when they edited (use INPUT.stats and per-shift edited_by_user). You MUST align any counts with INPUT.stats (do not contradict the numbers).
If INPUT is sparse, still return valid JSON with shorter text and conservative wording.
